## In-app chat with Muse (2026-11-03 edit)
- **Request**: "Now add yourself in the Muse App version so I can chat with you within the app" — a Chat tab + sidebar entry inside the artifact, in the original style (navy bottom tab, flame logo avatar, glossy red send button).
- **Channel**: `ctx.inference.complete` inside the `sendChatMessage` server action only (no client-side model, no third-party inference API). The model sees only data already in this app: a snapshot built from `ctx.db` rows + the user's own 1,477-car catalog (owned/missing names, Treasure Hunt flags, targets, hunt days, budget, streak, badges, car of the day). No web search, no prices, no store stock — the UI says so, and the model is instructed never to invent a car, price, or availability not in the snapshot.
- **Persistence**: `chat_messages` table (`drizzle/0003_add_chat_messages.sql`); `getChatHistory` / `sendChatMessage` / `clearChat` actions. History is the user's own messages plus Muse replies, saved in the artifact DB like every other record; `resetAll` also clears it.
- **Acting on chat**: when the model returns `mark_owned` / `mark_th` / `add_target` with a car name, the server fuzzy-matches that name against catalog + custom cars (exact, then unique substring/start, then best word overlap). It writes only on a single match and appends a grounded confirmation to the reply; on several matches or no match it writes nothing and says so in the reply. The model never claims a change is done before the server confirms it.
- **Failure behavior**: if inference fails, the user message is still saved and a grounded fallback reply (live owned/total/TH counts from the snapshot) is saved and returned, instead of throwing the error into the UI or inventing an answer.
- **No external source**: no new web source was used for this edit; no URLs were added.

## Photo delete fix (2026-11-03 edit)
- **Request**: "Somehow it won't let me delete a photo" — with a screen recording of the 16 Angels car sheet: tapping a photo's × opened the "Delete this photo?" confirm, tapping "Delete photo" closed the dialog, but both photos stayed and no "Photo deleted" toast ever appeared, twice in a row.
- **Diagnosis from the evidence**: the server `deletePhoto` handler deleted the stored blob *before* the database row, so any blob-cleanup failure aborted the whole delete; and the shared confirm dialog fired the delete fire-and-forget (`run()` with no await/catch), so a failure closed the dialog silently with no error shown. Direct sandbox invocations and probe taps of the gallery/car-sheet delete paths succeeded, so the failure was in that ordering + silent-swallow combination, not in the delete button itself. No durable photo was deleted by the builder during diagnosis (sandbox deletions only); which of the two near-identical 16 Angels photos Anthony wanted gone was never identified from the video, so none was removed for him — the fixed delete control is the remedy.
- **Fix**: `deletePhoto` (and the same pattern in `deleteVideo`, `deleteCustomCar`, `resetAll`, and `setProfilePhoto`) now deletes the database row first and removes the blob afterwards via a best-effort helper that swallows blob errors, so an already-gone/undeletable blob can never trap a row. The confirm dialog now awaits the action, disables its buttons while it runs, and on failure closes with a visible "That couldn't be deleted. Please try again." toast instead of silence. No schema change, no new source.
- **Load hardening (same edit, found while verifying)**: the first re-audit's capture failed to load with `/actions` 500 — `getState` threw `ctx.blobs key not found: photos/1793746882852-597347` for one sandbox photo whose stored blob was gone, because `loadState` called `ctx.blobs.getUrl` unguarded for every photo/video/profile photo. One missing blob bricked the whole app. `loadState` now resolves blob URLs through a best-effort helper: a missing blob yields an empty URL (profile photo: null), the row stays listed, and the client renders a "Photo unavailable"/"Video unavailable" placeholder (or the existing logo placeholder on tiles and car of the day) with its Delete control intact, so the orphaned row can still be removed. This was a sandbox-store divergence exposed by test deletions; durable data was untouched.
